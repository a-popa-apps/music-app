Investigated and ruled out: the specific file in isolation (processed cleanly alone and even with 3 concurrent copies of itself), a per-file memory leak (20 sequential runs in one process showed memory plateau, not unbounded growth), and the earlier OOM issue (real memory usage stayed well under the 2GB limit at the moment of each crash) — the exact trigger was never pinned down, but the right fix doesn't depend on knowing it. Disk absorbs a multi-GB batch fine; RAM doesn't. ## Product ideas — nice to have

From a product-improvement pass on 2026-09-15 (full list had 6 ideas; #1 playback/waveform, #3 inline correction of results, and #5 energy-heuristic tuning were picked to build now — see git history around this date). Parked here for later:

- [ ] Surface BPM/key confidence in the results table — `detect_bpm.py`/`detect_key.py` already compute confidence internally (key detection even retries below a 0.7 threshold), it's just never shown to the user. Cheap: the data already exists, this is purely a UI addition (e.g. a "double-check this one" flag on low-confidence rows).
- [ ] **Reward successful referrals from the invite system** (e.g. bonus tracks that period once an invite's `accepted_uid` gets set) — deliberately not built alongside the invite system itself (shipped 2026-09-16, see Reliability section above); would touch `profile_store.py`'s quota/usage code, which is billing-sensitive and already handled carefully twice this session (the quota-race-condition fix and the retag-quota fix) — needs the same care, not a rushed bolt-on.
- [ ] Native Rekordbox XML / Serato crate export, not just ID3 tags + a generic `.m3u8` — would be a real differentiator since DJs live inside those tools daily rather than raw folders of tagged files. Bigger lift: need to learn each tool's export format.
- [ ] **Duplicate detection across a batch (or a user's whole history) via audio fingerprinting** — DJs often accumulate the same track ripped from multiple sources under different filenames. Scoped 2026-09-16:
  - **Fingerprinting method — Chromaprint/AcoustID (the industry standard, what MusicBrainz itself uses) confirmed NOT viable on this backend's current Render setup**, verified with a real throwaway-venv install rather than assumed: `get_service` confirms the backend deploys via `pip install -r requirements.txt` only (no Dockerfile, no `apt-get` step). `pip install pyacoustid chromaprint` succeeds, but the PyPI package literally named `chromaprint` is an unrelated colored-terminal-output library (a name squat) — `import chromaprint` "succeeds" but has none of the API (`Fingerprinter`, etc.) `pyacoustid.fingerprint()` actually calls, so it would fail at runtime, not at install time. The real fallback, the `fpcalc` command-line tool, isn't on `PATH` either (needs a system package, e.g. `apt-get install libchromaprint-tools`, which this build has no step for). Checked PyPI for a self-contained wheel bundling the binary (the way `essentia`'s wheel bundles FFmpeg) under several plausible names (`pyfpcalc`, `chromaprint-binaries`, `pyacoustid-fpcalc`) — none exist. Bottom line: Chromaprint needs either a Docker-based Render build (bigger infra change than this feature) or doesn't happen.
  - **Recommended path instead: a DIY fingerprint built on essentia alone** (chroma/HPCP or MFCC features, hashed into a compact fingerprint, compared by Hamming/cosine distance) — essentia is already a proven dependency in this exact deploy environment, so zero new deploy risk. Trade-off: unlike Chromaprint's real-world-tuned matching, a DIY version's false-positive/negative rate is unverified and needs testing against real "same song, different rip" pairs before trusting it in production — a genuinely separate, non-trivial task from writing the fingerprint code itself.
  - **Placement**: slots into `_run_essentia_analysis` in `process_audio.py`, which already decodes each file's audio into memory once inside the existing crash-isolated worker process (`analysis_process_pool.py`) — fingerprinting reuses that same in-memory audio, not a second decode pass, just extra CPU per file alongside the existing BPM/key/energy work. Inherited caveat: Free-tier only decodes the first `ANALYSIS_SECONDS` (30s) for speed, which is fine for BPM/key but weaker for fingerprint matching, since two rips of the same song don't always share identically-timed intros — Pro's "Enhanced Detection" (full-track decode) would be more reliable here.
  - **Two genuinely different comparison scopes**, matching both cases named above:
    1. *Within a batch* (works for anonymous trial users too) — cheap, in-memory pairwise comparison among the handful of files in one upload.
    2. *Against a user's history* — `history_store.py` already persists per-track metadata (BPM/key/genre/duration, never audio) per logged-in user; a `fingerprint` field fits there naturally. Comparison would be a linear scan of that user's own existing fingerprints (bounded and cheap at real per-user history sizes). This only works as a **per-user** feature, not a global "has anyone anywhere uploaded this" one — Firestore can't do real similarity search, and a global version would need actual vector-search infra. That matches what was actually asked for, not a limitation in practice.
  - **Surfacing**: a new manifest field (e.g. `duplicate_of`, referencing the matching filename/history entry) shown as a non-blocking badge in the results table — flag it, don't stop the download, since the use case is "help me notice I have this twice," not "refuse to process it." Needs a small frontend addition too, not just backend.
  - Not started — this is scope only.
- [ ] Loudness normalization (e.g. to a target LUFS via ReplayGain/EBU R128 tags, or actually adjusting gain) — right now CratePrep detects and tags but never touches level, so a set built from mixed sources can still have jarring volume jumps track-to-track. `essentia` (already a dependency) has loudness-estimation tools (`Loudness`/`LoudnessEBUR128`) to build on; writing a gain tag is cheap, actually normalizing audio is a bigger lift (re-encode cost, format-specific gain application).
- [ ] **Show each file in the results table as soon as it's analyzed, instead of waiting for the whole batch** — user request 2026-09-16, after noticing large batches spend a long time uploading before anything shows on screen. Today `/process` is one request in, one finished zip out, so upload time and analysis time happen back-to-back and the table only appears once everything is done. Scoped plan:
  - Split into one request per file (or small group) instead of one request for the whole batch, so each file's result comes back and can be shown the moment it's ready — upload of the next file overlaps with analysis of the previous one instead of waiting.
  - Move the batch-quota check (monthly track limit / anonymous trial limit) to a single upfront call before any file uploads, sized to the whole batch's file count — not re-checked per file, or someone could exceed their limit by uploading one file at a time.
  - Move the AI batch summary (the one-line "this batch is a steady house mix at 90 BPM" text) and the final downloadable zip to a last step that runs once every file has finished, since both genuinely need the whole batch's data together.
  - Build the final zip in the browser from the already-downloaded per-file pieces (frontend already uses `fflate` for unzipping, likely has `zipSync` too) instead of the server re-assembling it — avoids a second, redundant processing pass just to package the download.
