- [x] **Analysis result caching, so the same track doesn't get re-analyzed from scratch by every user who uploads it** — two independent, global (cross-user) Firestore caches added in `backend/app/analysis_cache.py`: (1) an exact-match cache keyed by a SHA-256 of the raw uploaded bytes — a hit means literally the same file was already fully analyzed before, so `build_zip` skips both the essentia decode/analysis and the genre catalog lookups entirely and reuses the full prior result; (2) a metadata-only cache keyed by normalized artist+title, wired into `detect_genre.py`, that only shares genre/artwork (looked up once, wired into every `detect_genre()` call regardless of caller) — this is what actually covers the common "same song, different rip" case (e.g. an MP3 upload and a longer FLAC rip of the same track are completely different bytes and would never hit the exact-match cache, but genre/artwork don't change between rips of the same official release, so it's safe to share). - [x] **A single bad file could crash the entire backend for every user** — confirmed live in production: a real 30-file batch upload crashed the whole Render instance mid-batch, three times in a row at the exact same point, killing every other in-flight request too (not just the uploader's). Root-caused to essentia/ffmpeg's native (C++) decode/encode pipeline occasionally segfaulting outright on a real-world file — a segfault kills the entire OS process, and `_analyze_and_tag` ran in a thread (`run_in_threadpool`), so all threads (every concurrent request) shared that one process and died with it. Investigated and ruled out: the specific file in isolation (processed cleanly alone and even with 3 concurrent copies of itself), a per-file memory leak (20 sequential runs in one process showed memory plateau, not unbounded growth), and the earlier OOM issue (real memory usage stayed well under the 2GB limit at the moment of each crash) — the exact trigger was never pinned down, but the right fix doesn't depend on knowing it. Added `backend/app/analysis_process_pool.py`: the essentia/ffmpeg-touching steps (BPM/key/energy analysis, and separately the AIFF browser-preview generation) now run in isolated worker OS processes (`ProcessPoolExecutor`, `spawn` context — not the Linux-default `fork`, which is a documented hazard when gRPC connections already exist, as they do via firebase-admin/Firestore) instead of threads. A crash there now only kills that one worker; the pool detects it (`BrokenProcessPool`), recreates itself, and the rest of the server keeps running untouched — verified with a real, deliberately crashing worker process (`os._exit(1)`, the same failure mode as a segfault) that the parent process survives and the pool recovers for subsequent work. Tag-writing (pure Python/mutagen, no native-crash risk) stays in the main process and was deliberately kept out of the isolation boundary — an earlier version of this fix isolated the whole pipeline and it cost roughly 2x the intended overhead, since the entire re-tagged file (tens of MB) was being pickled back through inter-process communication for no reason; narrowing the isolated surface to just the two essentia-touching calls (bundled into one combined call on a cache miss, so a large file's bytes only cross the process boundary once, not once per essentia step) fixed that. Real cost measured: ~215MB per persistent worker process (`PROCESS_CONCURRENCY`, currently 3) for its own essentia/numpy import + whatever it's currently decoding, on top of the existing per-chunk buffer cost already accounted for in the original OOM fix — worst case measured (3 concurrent 91MB 24-bit AIFF files, deliberately close to the real crash scenario) came to ~1.38GB combined against the 2GB plan, still under budget but eating into the headroom the OOM fix established; worth watching via real Render metrics after this deploys. Shipped 2026-09-15.

- [ ] Native Rekordbox XML / Serato crate export, not just ID3 tags + a generic `.m3u8` — would be a real differentiator since DJs live inside those tools daily rather than raw folders of tagged files. Bigger lift: need to learn each tool's export format.
- [ ] Duplicate detection across a batch (or a user's whole history) via audio fingerprinting — DJs often accumulate the same track ripped from multiple sources under different filenames. The pipeline already decodes every file, so the raw signal is there; would need a fingerprinting/similarity step added.
- [ ] Loudness normalization (e.g. to a target LUFS via ReplayGain/EBU R128 tags, or actually adjusting gain) — right now CratePrep detects and tags but never touches level, so a set built from mixed sources can still have jarring volume jumps track-to-track. `essentia` (already a dependency) has loudness-estimation tools (`Loudness`/`LoudnessEBUR128`) to build on; writing a gain tag is cheap, actually normalizing audio is a bigger lift (re-encode cost, format-specific gain application).
